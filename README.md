# IOP

**A research environment for physical instruments and experimental platforms.**

[中文](README.zh-CN.md) · [Install](docs/runtime/README.md) · [Agent connections](iop/connect/README.md) · [Python and HTTP](docs/runtime/http-api.md) · [Research episodes](docs/runtime/episodes.md) · [Releases](https://github.com/Cherish0925/IOP/releases)

IOP combines a persistent Runtime, instrument descriptions, drivers, platform configuration, experiment programs, data records and agent connections. A research program communicates with one service; the service coordinates devices, executes dependencies and retains the results when the agent disconnects.

The environment is independent of the agent host. People, Agentic Research OS, Codex, Claude Code, Qiushi Engine and other clients use the same registered instruments and saved experiments through the supported SDK, HTTP or MCP entry point.

## Install and connect

Install from source with Python 3.10 or newer:

```sh
python -m pip install "ai4instruments[agent] @ git+https://github.com/Cherish0925/IOP.git"
iop init
iop start
iop open
iop connect --name bench --local
```

`iop desktop` opens the native desktop entry point when its optional dependencies are installed. Platform release archives include Python, the Rust executor and the core service/agent dependencies. The [release page](https://github.com/Cherish0925/IOP/releases) lists available builds; the [installation guide](docs/runtime/README.md) covers Windows, macOS, Linux, WSL and remote laboratory hosts.

For agent hosts, install the connector directory generated by `iop connect`, or register `iop mcp` in a compatible stdio MCP client. Named connections support local services, SSH and remote HTTP. The [connection guide](iop/connect/README.md) documents each host's format. A plugin connects to the service; installing it does not replace instrument drivers or laboratory configuration. An agent starts from a compact laboratory overview and a short working method, and reads the description of an instrument or a guide to one part of the work (`guide`, or `iop guide` in a terminal) when a task needs it, so what every turn carries stays small.

The [tasks for an agent](iop/agent-setup.md#tasks-for-an-agent) give copyable prompts for deployment, instrument and platform setup, experiments, research and continuation. Start from the laboratory's current state; save physical information supplied by the operator for later work.

## Organize one laboratory

| Part | Responsibility |
| --- | --- |
| Instruments | Installed driver or vendor SDK, identity, units, operation parameters and readbacks, and the limits a setup tolerates on its arguments. |
| Platforms | Physical wiring, shared devices, sample information and initialization procedures supplied by the researcher or agent. |
| Runtime | Device ownership, dependency scheduling, parallel branches, persistent programs, cancellation and stored results. |
| Research programs | Scientific decisions, algorithms, initialization choices, analysis and task-specific feedback. |
| Episodes | Initial observation followed by actions, observations and feedback linked to completed instrument operations. |

Initialization is explicit. Discovery can identify supported interfaces and devices; it does not infer sample preparation or the physical meaning of every cable. Independent platforms can run concurrently. A shared device remains coordinated by the same scheduler.

## Operations

Operations keep the three roles defined by [AI4Instruments](https://github.com/Cherish0925/AI4Instruments/blob/main/docs/operations.md). Each is something the Runtime stores and executes.

| Role | In IOP |
| --- | --- |
| **Basic Operations** | The operations of a registered device: one control or observation each, with parameters, units, ranges and readbacks. |
| **Standard Operations** | Saved methods built from Basic and Standard Operations, with parameters, conditions, a named result and a record of use. |
| **Workflow Operations** | Saved organizations of methods across devices: a step graph in sequence and in parallel, or a program that decides from results. |

A step with `device` is a Basic Operation; a step without it uses a saved operation by name. The Runtime expands saved methods into Basic Operations and records every use, so methods remain inspectable and reusable.

| Research task | Execution control |
| --- | --- |
| Scan and refine a range | `sweep` gathers scalar and array results. Ranges can read earlier results; adaptive scans place points from the readings so far. |
| Estimate variation or reach a stopping criterion | `repeat` takes repeated readings; `until` stops on a threshold or on an uncertainty computed from the gathered data. |
| Optimize a measured response | `seek` searches for a local maximum or minimum within declared bounds. |
| Recover interrupted work | Explicit `retry` repeats eligible failed calls. A stopped step graph can continue with its completed results preserved. |

Later steps can bind to gathered results, such as the angle of most power or the center of a fitted line. See [operations](docs/runtime/operations.md) for parameters, composition and recovery behavior.

## Operating conditions

Describe what the experiment needs: an observed quantity or state, its tolerance, and a method to restore it when applicable. These conditions can belong to an instrument or a platform. Experiments select them with `requires`; `upkeep` maintains them between operations or while the platform is idle. A changed sample, cable or enclosure can renew the affected conditions without repeating unrelated setup.

The runtime coordinates these operations with experiments and retains their observations. It marks measurements affected by drift or instrument status so the research program can assess or repeat them. Device bounds, units and timing stay in the instrument description. Read [operating conditions](docs/runtime/conditions.md) for the format and [apparatus knowledge](iop/connect/skills/iop-lab/references/priors.md) for calibration, settling, references and other physical considerations.

## Measured arrays

Traces, spectra, images and streams retain type, shape, units and axes. `read_array` provides summaries, selected windows, peaks and curve fits; full arrays remain downloadable as NumPy files. Rust `iop-execd` handles large files outside the service, with a matching Python implementation. Later operations can use the results. See [reading arrays](docs/runtime/drivers.md#reading-arrays--读取数组).

## Measurement methods

Research programs can use `ai4instruments.iop.measurements` for streaming means and first-order uncertainty propagation. Named error contributions preserve covariance: a common calibration error remains shared when readings are averaged, and a common gain cancels when a ratio permits it. Units and signed sensitivities stay with the estimate.

The [reference measurement program](examples/iop/reference-measurement/) acquires configurable signal, dark and reference readings, records the raw acquisitions, and stops at a chosen standard uncertainty or sample limit. It saves progress through the existing experiment API and resumes without repeating completed operations. Read [measurement reduction](iop/connect/skills/iop-lab/references/measurements.md) for assumptions and use outside this example.

## Research and learning

Keep research decisions with their experiments and recover them across conversations. Episode records link actions, observations and feedback to completed instrument operations; JSON Lines exports support downstream learning. An experiment exports as a ZIP of its records and files with an RO-Crate description. The research program defines its scientific objective and learning algorithm. Physical preparation uses the platform's procedures and available resources. See [research guidance](iop/connect/skills/iop-lab/references/research.md) and [episodes](docs/runtime/episodes.md).
